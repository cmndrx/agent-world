# Agent World audit — October 8, 2026

Scope: one authorized audit of the current checkout and running packaged app. No application changes, real prompts, queue changes, acceptance, schedules, provider spending, publishing, commits or pushes. Existing uncommitted work was preserved. This is a product and implementation critique, not a complete security or performance certification.

## Honest verdict

Agent World has a distinctive identity and substantial working infrastructure. The neighborhood, project homes and persistent residents give otherwise abstract agent work a place and a personality. It is much more than a visual mockup.

But it currently has more feature breadth than workflow coherence. It combines a spatial activity observer, a full agent chat/automation client and a cozy progression game. Each has promise; their connection is still weak. My judgment: a compelling working prototype, not yet a dependable daily command center or a fully satisfying game. The next value milestone should be making one complete work-and-review loop obvious and trustworthy, rather than adding another surface.

## What is strong

- The visual identity is recognizable. The homes/residents metaphor makes project ownership tangible, and the dark panels are generally readable against the world.
- The implementation takes important boundaries seriously: resident/chat ownership, scoped execution, human acceptance, attachment integrity and separation of simulated flavor from observed activity. Tests and source support these mechanisms; they do not prove every real-provider path works.
- The feature set is substantial: resident conversations, provider/model controls, attachments, projects, review and local scheduling. Scheduling has explicit local-runtime limitations and failure handling rather than pretending to be cloud automation.
- Existing tests cover meaningful ownership and authorization cases. The package currently matches checkout assets and passes signature verification.

## Prioritized findings

### 1. High priority: a watcher failure can crash the bridge

Fresh isolated API tests failed. Diagnostic reruns of `test/cli-api.test.mjs` captured both spawned bridges exiting with an unhandled `FSWatcher` error: `EMFILE: too many open files, watch`, exit code 1. The live app stayed responsive during the audit.

`bridge/inbox.mjs` catches synchronous `fs.watch()` setup errors but does not attach an asynchronous watcher error handler. Its two-second polling safety net cannot protect a process that exits on the unhandled event. The resource trigger is environmental; the missing recovery is an application robustness defect. I did not establish which other process consumed the watcher resources, and did not change system limits or terminate processes.

This should be addressed before expanding automation. A passing suite on an earlier machine/session does not resolve this fresh failure.

### 2. High product priority: chat and the work board tell different stories

The live Work Now view showed seven review items waiting roughly three days and an older next action about the review pilot/measurement. The prompter contained newer work and responses. The board was not an effective summary of the current conversation workflow.

Human acceptance must remain explicit. The problem is the missing clear handoff from a chat result to an actionable review and then visible project progression. Someone can accomplish work through the prompter while the neighborhood's task/progression layer feels stale or requires separate administration. That undermines the central promise of seeing a project move forward.

The prior work-loop report also records missing matched benefit measurements. This audit did not collect a fresh time-saved or user-outcome study. We should not equate the number of features or completed turns with proven usefulness.

### 3. Medium priority: reviewing outputs is weaker than composing prompts

The live chat displayed literal Markdown file links instead of usable artifact links. `web/src/pass-card.js` escapes message text into plain content; `shared/chat.mjs` flattens structured results into message text. Escaping is appropriate, but the reader loses useful report formatting and direct artifact navigation. Long prompt-derived conversation titles also become difficult to distinguish when truncated.

Results are capped at 2,000 summary characters in `bridge/passes.mjs`. That encourages short status reports even when the user asks for a substantial audit. A concise summary plus an accessible report/artifact is a better fit. The whole-panel rendering approach also produced stale accessibility targets during inspection; actual typing/focus and screen-reader behavior need targeted testing before calling them broken.

### 4. Medium priority: the world implies more capability than some paths deliver

Voice is exposed as a conversational control, but README and observed history describe the default Codex realtime path rejecting ChatGPT subscription authentication and producing no audio. I did not initiate voice or test paid API authentication. Its experimental/authentication limits should be clear before a user tries it.

Game-launched CLI passes are globally serialized: `PassStore.claimNext()` blocks claims while any run is running or interrupted, and the runner has a single busy guard. This is a reasonable safety tradeoff, but multiple residents can suggest a parallel team. An interrupted run can block everyone. External observed sessions are a separate layer and may run concurrently; this is not a claim that all activity is serialized.

### 5. Medium product priority: the game layer needs a clearer reward loop

The world is charming at a glance, but large chat/work panels obscure it, and chat blurs most of the neighborhood behind a nearly full-screen interface. At the moment the core utility is largely two-dimensional, with the world often becoming background scenery.

House upgrades, decor and resident activity would be more satisfying if the user could clearly understand which verified outcomes changed the world and why. Avoid awarding progress merely for a finished turn. The goal is meaningful feedback for human-reviewed outcomes, with less bookkeeping.

Visual polish also has room to improve: rain remains visible through exposed cutaway interiors, and a bright selected-resident halo can obscure the small character. These are observational polish judgments, not evidence that the renderer is generally defective.

### 6. Maintenance and performance need evidence before further breadth

The current main JavaScript bundle is approximately 1 MB. The animation loop continues landscape, residents, weather and rendering work while chat is open. Adaptive rendering quality is already present, which is good. I did not benchmark CPU, frame rate, battery use or large neighborhoods, so I cannot honestly call the app slow.

Several large UI modules and dense templates now carry many overlapping responsibilities. README and navigation documentation retain older descriptions alongside newer behavior—for example model switching and entry points. This makes onboarding and maintenance harder. Documentation should describe the current product consistently rather than accumulating incompatible eras.

## Checks actually run

- Read project instructions, CONCEPT, README, latest handoff, repository Agent World skill and relevant workflow/navigation references; inspected current Git changes and implementation paths.
- Read-only native Electron inspection: neighborhood/prompter, Connections and Work Now. No task dispatch or acceptance. The user changed app state during a later navigation attempt; no further disruptive interaction was attempted.
- Read-only `/api/state`: HTTP 200. Verified the listener on port 4777 was the packaged-app bridge. Raw state includes preserved hidden homes; it is not a count of homes displayed in the selected world.
- `npm test` on Node 18.16.0: **186 tests, 179 passed, 4 failed, 3 cancelled**. API failures reported fetch errors; catalog cancellations followed unfinished promises.
- `node --test test/cli-api.test.mjs`: both tests failed again. Temporary diagnostic preloads captured underlying connection errors and both isolated bridge exits from the asynchronous `EMFILE` watcher error. That cause was directly established for this subset; not independently proven for every full-suite failure.
- `codesign --verify --deep --strict` passed for `release/mac-arm64/Agent World.app`.
- SHA-256 comparison: all packaged dist (8), bridge (20) and shared (23) files matched checkout.
- `git diff --check` passed before the audit documentation update and was run again afterward.

No fresh app build was needed or run: this pass changes documentation only. The existing package was verified, and the running app was not restarted while work was active. Prior handoff claims of 186/186 passing are historical, not this audit's result.
